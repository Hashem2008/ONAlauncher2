physx-jni facts (javap on de.fabmax:physx-jni 2.2.2 and 2.3.1, readelf on physx-jni-android 2.3.1):
- 2.2.2 reads physxjni.nativeLibLocation / physxjni.loadFromResources (loads <dir>/<lib name>).
- Native methods: 4554 in both; 7 differ (JniThreadManager._init gone, PxSceneFlag eSUPPRESS/
  eFORCE_READBACK -> eENABLE_DIRECT_GPU_API, vehicle2 "Renponses" typo fixed, tank nbWheelsInTracks
  replaced). The Android library lacks 533 GPU/CUDA/particle/OmniPVD methods (all versions).
- Android build: arm64-v8a only, 63 MB .so in a 17 MB aar, 4 KB page aligned, has JNI_OnLoad.

Fix (no change to the mod):
- tools/physx-compat: libPhysXJniCompat.so (arm64, -nostdlib, 16 KB aligned, DT_NEEDED
  libPhysXJniReal.so + RUNPATH $ORIGIN) implements the 7 methods (forwards the renamed vehicle2 pair).
  Built with build.sh (clang + lld), committed to jniLibs/arm64-v8a. Every one of 2.2.2's natives
  resolves to the real library or the bridge (script check, 0 unresolved outside GPU features).
- PhysxSupport: BRIDGED_VERSIONS 2.2.2 -> 2.3.1. prepare() downloads Android 2.3.1 (existing Maven
  download), builds <cache>/physx-android/2.2.2-bridge (bridge as libPhysXJniBindings_64.so, real as
  libPhysXJniReal.so; copied when size / time changed), status READY "2.2.2 (Android 2.3.1)".
  jvmArgs() points physx-jni at that folder. arm 32-bit and x86_64 APKs: as before (reported).
Not device-tested. Risks: PhysX 5.3 under 2.2.2's Java side (identical signatures, values of enums
come from the native side); a GPU-physics option in the mod would hit the missing GPU methods.

"Failed loading native PhysX", Physics Mod listed without CONSTRUCT errors.
